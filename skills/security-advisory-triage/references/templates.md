## 1. 優先序定義

建議時程是沒有合約 SLA 時的預設提案，寫進矩陣時標示「建議，待客戶確認」。

| 優先序 | 條件（符合任一） | 建議處置時程 |
|---|---|---|
| P1 | 攻擊面可由 Internet 或不受信任網路到達，且符合任一項：已遭利用或列入 KEV、Critical、未經驗證的 RCE、含 Critical/High 但細節尚未公開的預告型或 hardening 修補 | 當日完成暴露面緩解；細節公開日前的第一個可用窗口升級 |
| P2 | 已遭利用或 Critical，但攻擊面只在受控的內部或管理網段；High 且攻擊面對外 | 72 小時內完成緩解；下一個例行窗口升級，且早於細節公開日 |
| P3 | 需要驗證且攻擊面只在受控管理網段；Medium 以下但影響核心設備 | 例行維護週期內升級 |
| P4 | 不受影響但需留檔；Low；功能未啟用 | 併入下一次版本治理 |

「有沒有在野利用」不是 P1 的必要條件。管理介面對 Internet 開放、又有 Critical/High 修補待上的設備，就算沒有 CVE 也是 P1。

暴露面不明、又會改變優先序時，標「需確認」並給確認期限。確認前先排低成本的暫時緩解，升級的優先序等確認後再定。

同一筆通報在不同客戶可能落在不同優先序，因為暴露面不同。優先序跟著「資產 × 通報」走，不是只跟著通報走。

## 2. 狀態值

| 狀態 | 意義 |
|---|---|
| 待查證 | 還沒對到原廠一手來源 |
| 待人工複核 | 使用者沒點名、由分析過程自行加入的項目，需工程師核實後才採用 |
| 待資產確認 | 缺版本、功能啟用或暴露面資訊 |
| 待排程 | 判定受影響，尚未排定窗口 |
| 已排程 | 已有窗口與 owner |
| 已緩解 | 只完成暫時緩解或補償控制，仍需升級 |
| 已修補 | 已升到原廠修補版本，並有版本證據 |
| 風險接受 | 客戶書面接受，附期限與複查日 |
| 不受影響 | 已比對 exact version 或功能未啟用，附證據 |
| 已轉交 | 非本團隊設備，已交給對應 owner |

「已緩解」不能直接跳到結案。要嘛升級變成「已修補」，要嘛取得客戶書面「風險接受」。

## 3. 修補追蹤矩陣欄位

| 欄位 | 填寫方式 |
|---|---|
| 項目 ID | `<年週>-<廠牌>-<序號>`，例如 `2026W43-FTNT-01` |
| 來源 | 收到的管道與日期，例如「經銷商通知 10/24」；多來源全部列出；分析時自行加入的項目寫「自行加入」 |
| 查證狀態 | 已查證／與原廠不符／查無官方資料／僅廠商宣稱 |
| 廠牌／產品 | 寫到產品線，例如 FortiManager、Panorama M-Series |
| Advisory／CVE | 原廠 ID 與 CVE；預告型通報沒有 ID 時寫原廠公告標題與日期 |
| 嚴重度 | 原廠評級與 CVSS 版本 |
| 利用狀態 | 原廠用語原文，例如 very limited exploitation；附 KEV 狀態 |
| 受影響條件 | 版本範圍加功能前提，例如「管理介面可達且需已驗證帳號」 |
| 客戶／站點 | 沒有資產清單時填 TBD |
| 資產 | 型號、角色、HA/cluster 成員 |
| 目前版本 | exact build 與 hotfix；不知道就寫「待確認」 |
| 判定 | 受影響／不受影響／需確認／EoS 無修補 |
| 目標版本 | 原廠修補版本；同時是 Preferred/Recommended 時註明 |
| 升級路徑 | 需要的中繼版本，依 Upgrade Path Tool 或原廠文件 |
| 暫時緩解 | 原廠 advisory 列出的 workaround 或限制暴露面的做法 |
| 補償控制（選配） | 特徵碼、virtual patching 等，附前提：授權、content 版本、流量路徑、解密 |
| 優先序 | P1–P4 |
| 負責人 | 我方與客戶各一位；不知道人名時寫角色或團隊，例如「我方 NE」「客戶系統組」，不要留空 |
| 期限 | 緩解期限與升級期限分開寫 |
| 狀態 | 見第 2 節 |
| 驗證證據 | 版本截圖或 CLI 輸出的存放位置 |
| 查核日期 | 最後一次對原廠來源的日期 |

## 4. 資產清單最少欄位

沒有設備清單時，向內部或客戶要下列資訊；每一欄都會影響判定或排程：

- 客戶、站點、設備型號、角色（邊界、資料中心、分支、管理平台）。
- HA 或 cluster 角色與成員。
- 管理方式：Panorama、FortiManager、Central、Mobility Conductor、本機。
- 目前 exact version，含 hotfix 或 patch。
- 管理介面暴露：是否可由 Internet 或不受信任網路存取、是否設 trusted hosts 或來源限制。
- 對外服務：VPN portal、SSL VPN、對外發布的服務。
- 已有授權：IPS/Threat Prevention 類訂閱、support 合約到期日。
- 維護窗口、變更審核流程與客戶窗口。

## 5. 升級排程表

| 批次 | 優先序 | 日期／窗口 | 客戶／站點 | 設備與執行順序 | 版本（從 → 到） | 前置條件與依賴 | 升級前的暫時緩解 | 回滾點 | 執行／覆核 | 狀態 |
|---|---|---|---|---|---|---|---|---|---|---|

排程時檢查：

- 管理平台先於被管設備，且版本大於等於被管設備。
- 同一 HA pair 不跨窗口拆開升級，除非 subskill 的程序明確允許。
- 每批的第一台是可接受失敗的設備，並在擴大前設定 go/no-go 判斷點。
- P1 的暫時緩解另排時間，不等升級窗口。
- 日期避開國定假日與補假；跨午夜的窗口寫出起訖日期。
- 同一時段有多位客戶的窗口時，標出人力衝突。
- 「執行／覆核」不知道人名時寫角色或團隊。

## 6. MOP 草稿骨架

```text
MOP：<客戶> <產品> 升級至 <目標版本>（<批次 ID>）
狀態：草稿，待工程師審核與客戶核准

1. 目的與範圍
   - 對應通報：<項目 ID 與 Advisory/CVE>
   - 設備：<TBD:型號、角色、HA 成員>
   - 影響：<TBD:預期中斷時間與受影響服務>
   - 窗口與變更單：<TBD>

2. 角色與聯絡
   - 執行：<我方 NE 或人名>  覆核：<我方資深工程師或人名>  客戶窗口：<客戶團隊或人名>  原廠 case：<若有>

3. Pre-check（每項附預期結果）
   - 目前版本與 HA 狀態
   - 設定備份與匯出位置
   - 路由、VPN、session 數、CPU/記憶體基準
   - 目標映像檔已下載並核對 checksum
   - Console/OOB 可用
   - 目標版本 release notes 的 Special Notices 與 Known Issues 中影響本案的項目，逐條列出 bug ID 或段落與因應做法
   - 依賴產品（管理平台、日誌平台）已升到相容版本

4. 執行步驟
   - 依 <廠牌 subskill> 的升級程序，逐步寫出設備、模式、指令或 GUI 路徑與預期結果
   - 未確認的語法標示 <TBD:待官方文件確認>

5. 驗證與 go/no-go
   - 每個階段結束時要看到的結果；不符合就停止

6. 停止條件
   - <TBD:例如 HA 無法同步、路由鄰接未恢復、關鍵服務中斷超過 N 分鐘>

7. Rollback
   - Trigger、步驟、所需時間、回滾後驗證

8. Post-check 與監控
   - 監控期間、客戶確認、矩陣狀態更新與證據存放
```
